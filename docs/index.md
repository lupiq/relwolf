## Who is it for?

relwolf fits you if:

- you host on **GitLab** (gitlab.com or self-managed) and want release automation that works the same as on GitHub,
- you want a **human to approve every release** by merging a release request,
- you want **control over the changelog** through [git-cliff](https://git-cliff.org) templates,
- you release a **monorepo** or keep versions in several files and ecosystems,
- you already write **Conventional Commits** or are happy to start.

It is probably not the right tool if you need a fully hands-off pipeline that publishes on every merge, or if you do
not want to follow Conventional Commits and do not use Changesets.

## How it works

You keep writing [Conventional Commits](https://www.conventionalcommits.org/). relwolf does the rest in a single CI job
on every push to your default branch.

  </li>

<p class="rw-note">The screenshots show relwolf releasing itself: <a href="https://github.com/lupiq/relwolf/pull/33">release request #33</a>.</p>

```text
feat: add search         → release request "Create release v0.1.0" opened
fix: typo                → release request updated (still v0.1.0, changelog has both)
(release request merged) → tag v0.1.0 + release created
fix: crash on start      → release request "Create release v0.1.1" opened
```

Git is used read-only, every step is idempotent and the release request is the only state. See
[How it works](/guide/how-it-works) for the details.

## Quick start

relwolf needs squash merging, the full git history and an access token stored as `RELWOLF_TOKEN`.

::: code-group

```yaml [GitHub Actions]
# .github/workflows/release.yml
name: Release
on:
  push:
    branches: [main]
concurrency:
  group: release
permissions:
  contents: write
  pull-requests: write
jobs:
  relwolf:
    runs-on: ubuntu-latest # Linux runners only
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0 # relwolf needs the full history and all tags
      - uses: lupiq/relwolf@v0 # x-relwolf-major
        with:
          token: ${{ secrets.RELWOLF_TOKEN }}
```

```yaml [GitLab CI]
# .gitlab-ci.yml
relwolf:
  image: ghcr.io/lupiq/relwolf:0 # x-relwolf-major
  stage: release # add it to your `stages:` or use an existing stage
  resource_group: relwolf
  variables:
    GIT_DEPTH: 0 # relwolf needs the full history and all tags
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  script:
    - relwolf
```

:::

Step by step: [GitHub guide](/guide/github) (tokens, GitHub App, repository settings) and
[GitLab guide](/guide/gitlab) (token scope, merge method).

## Configure what you need

`relwolf.yaml` is optional. Without it relwolf releases a single root package and updates no files. Add one to keep
version files in sync or to release a monorepo:

```yaml [relwolf.yaml]
# yaml-language-server: $schema=https://relwolf.lupiq.io/schema.json
patch-types: [fix, build]
packages:
  '.':
    updaters:
      - type: package-json
  services/api:
    component: api # tags: api-v1.2.3
    updaters:
      - type: pom-xml
```

- [relwolf.yaml reference](/configuration/relwolf-yaml): all options
- [Updaters](/configuration/updaters): version files, markers and lockfiles
- [Monorepos](/configuration/monorepos): linked versions, separate requests, one tag per group
- [Changelog](/configuration/changelog): git-cliff templates and `rewrite-changelog`
- [Pre-releases](/guide/pre-releases) and [Controlling the next version](/guide/release-as)

## relwolf and release-please

relwolf follows the workflow of Google's [release-please](https://github.com/googleapis/release-please). release-please
is excellent, but it exists for GitHub only. relwolf brings the same review-first workflow to **GitLab** and runs
equally on GitHub.

|                 | relwolf                                                           | release-please                                        |
| --------------- | ----------------------------------------------------------------- | ----------------------------------------------------- |
| Platforms       | GitLab and GitHub                                                 | GitHub only                                           |
| Changelog       | git-cliff: a `cliff.toml` controls the whole format               | Sections per commit type, `default` or `github` notes |
| Versioning      | Conventional Commits or Changesets                                | Conventional Commits                                  |
| Reverted commit | Cancels the original; both stay out of the changelog              | Listed in a `Reverts` section                         |
| Custom steps    | `pre-commit-script` can change any file before the release commit | No equivalent in its documentation                    |

See the [full comparison](/guide/comparison), including where release-please goes further.

## Good to know

- Supported platforms are GitLab and GitHub.
- relwolf is distributed as a [Docker image](/reference/docker-image) (linux/amd64 and linux/arm64) and as a GitHub
  Action (Linux runners only). It is not published to npm.
- It needs squash merging and a full clone; shallow clones abort with an error.
- Only release requests from relwolf's own release branch in the same project are tagged. Labelled requests from forks
  or other branches are skipped.
- Existing tags and changelogs can be kept, see [Migrating changelogs](/guide/migrating).
- Something not working? See [Troubleshooting](/reference/troubleshooting).
