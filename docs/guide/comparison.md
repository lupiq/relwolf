# relwolf vs. release-please

relwolf follows the workflow of Google's [release-please](https://github.com/googleapis/release-please): a release
request collects the changes, and merging it creates the tag and the release. release-please is an excellent tool, but
it exists for **GitHub only**. relwolf brings the same review-first workflow to **GitLab** and runs equally on GitHub.

This comparison is based on the source code and documentation of release-please 17.11 and on relwolf's own code and
tests. Both tools evolve; check their documentation for the latest state.

## At a glance

|                   | relwolf                                                                                                                                                                    | release-please                                                                                                                |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Platforms         | GitLab (gitlab.com and self-managed) and GitHub (github.com and Enterprise)                                                                                                | GitHub only                                                                                                                   |
| Run as            | Docker image (GitLab CI) or GitHub Action; one CI job, no daemon                                                                                                           | CLI and GitHub Action                                                                                                         |
| Merge method      | Squash merging                                                                                                                                                             | Squash merging recommended; merge commits work too                                                                            |
| Versioning        | Conventional Commits or [Changesets](/configuration/changesets)                                                                                                            | Conventional Commits                                                                                                          |
| Changelog         | Generated by [git-cliff](/configuration/changelog); a `cliff.toml` controls grouping, templates, links and the rest of the format; can be regenerated after config changes | Sections per commit type (`changelog-sections`); notes type `default` or `github`; custom templates only through the code API |
| Revert commits    | A revert cancels the original commit; both stay out of the changelog                                                                                                       | Listed in a `Reverts` section                                                                                                 |
| Forcing a version | [`RELWOLF_RELEASE_AS`](/guide/release-as) at runtime (pipeline variable or action input), per component, stored in the release request                                     | `Release-As:` commit footer or `release-as` in the config file                                                                |
| Version files     | [Typed updaters](/configuration/updaters), `generic` marker comments, globs and lockfiles                                                                                  | Release types per ecosystem and `extra-files` (`generic` markers, JSONPath and XPath updaters)                                |
| Monorepos         | [Packages with components](/configuration/monorepos), linked versions, one tag and release per linked group, one or several release requests                               | Manifest with components, `separate-pull-requests`, `linked-versions` plugin, workspace plugins                               |
| Custom steps      | [`pre-commit-script`](/configuration/relwolf-yaml#pre-commit-script) can change any file before the release commit                                                         | No equivalent in its documentation                                                                                            |
| Configuration     | One [`relwolf.yaml`](/configuration/relwolf-yaml) with a [JSON schema](https://relwolf.lupiq.io/schema.json); no CLI flags                                                 | JSON config and manifest files, CLI flags                                                                                     |

## Where relwolf is different

- **GitLab support.** The same workflow on gitlab.com and self-managed GitLab, with the same configuration as on
  GitHub. See [GitHub vs. GitLab](/reference/github-vs-gitlab).
- **A changelog you can shape.** Because [git-cliff](https://git-cliff.org) renders the changelog, you control the
  format with a `cliff.toml`: groups, templates, header, footer, links and release emoji. With `rewrite-changelog`,
  relwolf regenerates existing changelogs after you changed the template.
- **Changesets as an alternative.** Teams that describe changes in files instead of commit messages set
  `strategy: changesets` and keep the release request, tags and releases.
- **A hook for everything else.** The `pre-commit-script` runs before the release commit, for example to format the
  generated changelog.
- **Version requests at runtime.** Force a version from a manual pipeline or workflow run. The request is stored in the
  release request and survives later runs until you merge or remove it.
- **Reverts are understood.** A reverted commit does not appear in the changelog and cannot trigger a release.

## Where release-please goes further

- Built-in release types for many ecosystems.
- Workspace plugins that bump dependants (Node, Cargo, Maven). With relwolf, the Changesets strategy covers dependants
  in JavaScript workspaces.
- A `patch` marker and start/end marker blocks for generic files, plus JSONPath and XPath updaters. relwolf's `json`,
  `yaml` and `toml` updaters use dotted key paths without array indices.
- Support for merge commits next to squash merging.

## Which one should I use?

- Your code is on **GitLab**: use relwolf.
- You want **full control over the changelog format**, or you prefer **Changesets**: relwolf.
- You are on **GitHub** and rely on release types for many ecosystems, dependant bumping or merge commits:
  release-please may fit better.
- Both give you the same safety net: nothing is tagged until a person merges the release request.

relwolf and [semantic-release](https://github.com/semantic-release/semantic-release) both derive versions from commit
messages. In relwolf, every release passes through a reviewable merge request before anything is tagged or published.
